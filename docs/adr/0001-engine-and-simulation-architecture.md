# ADR-0001: Engine and simulation architecture

- Status: Accepted
- Date: 2026-09-07
- Sprint: 1, Day 1
- Deciders: Tho Dinh (owner)

## Context

Dink: Pickleball Rivals is a 3D pickleball game intended for a Steam release,
with shot physics modelled on TopSpin 2K25 and on real pickleball ball
behaviour, and with breadth of modes including doubles. The project starts
from an empty repository. Two decisions had to be made before any code was
written: what runtime to build on, and how to separate simulation from
rendering.

Three runtimes were considered.

Unity 6 is the industry default for a sports title of this shape and has the
most direct Steam path. Godot 4 is free, exports natively, and its source
files are plain text. Three.js with TypeScript runs in the browser and reaches
Steam only through a wrapper such as Electron.

## Decision

Build the game in TypeScript on Three.js, with the simulation written as a
pure, renderer-free module.

The runtime choice turns on iteration speed rather than on final packaging.
The work in this project happens in a cloud sandbox with no Unity or Godot
editor, so in either of those the code could be written but never run, and a
physics model that cannot be executed cannot be validated. Three.js can be
built, tested and screenshotted in the same environment on every change. A
Steam build later goes through Electron, which several shipped titles already
use; the risk that carries is accepted below.

The architectural half of the decision matters more than the runtime half.
`src/sim` imports nothing from Three.js. It owns vectors, ball state,
aerodynamics, impacts, court geometry and the event stream. `src/render` owns
meshes and cameras and reads sim state. `src/core` owns the fixed-timestep
loop. This means:

- The physics is unit-testable headless, and today it is: 25 tests run in
  under half a second with no browser.
- The simulation is deterministic and framerate-independent, so replays and
  future netcode have a foundation rather than a rewrite.
- If the runtime decision is revisited, the layer that encodes the actual game
  ports across; only the renderer is thrown away.

Supporting choices:

- Fixed 120 Hz simulation with an accumulator and render interpolation.
  Physics must not depend on the display refresh rate, or a 144 Hz player gets
  a different ball flight from a 60 Hz player.
- Semi-implicit Euler rather than RK4. It is first order, but it is symplectic,
  cheap, and bit-for-bit reproducible, which is what determinism needs.
- SI units and a single documented coordinate frame, stated once in
  `constants.ts` and referenced everywhere.
- Constants are labelled either as sourced from the USA Pickleball
  specification or as TUNED, so tuning for feel never silently overwrites a
  measured fact.

## Consequences

Positive:

- Every change can be verified in one command: typecheck, tests, production
  build.
- Physics bugs surface as failing tests rather than as "that felt wrong".
- Presets are generated by a tuner against the live constants
  (`tools/tune-presets.ts`), so changing drag cannot leave a serve that no
  longer lands in the box.

Negative, and accepted:

- Steam distribution needs an Electron wrapper, which costs binary size and
  some platform integration work. This is deferred to Sprint 5 and should be
  spiked early rather than at the end.
- Three.js gives no editor, so content authoring is code and data. For a
  two-player court sport with one ball this is a small cost; it would be a
  large one for a game with hand-built levels.
- WebGL performance ceilings are lower than a native engine's. Nothing in the
  current design approaches them.

Revisit this decision if the Electron spike in Sprint 5 shows an unacceptable
input-latency or controller-support gap.
